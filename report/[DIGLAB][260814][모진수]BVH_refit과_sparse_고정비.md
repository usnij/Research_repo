# sparse 학습에서의 BVH 재구축 비용과 refit

작성일 2026-08-14 · 모진수 · 대상 EVER (bonsai, downsampling 2), 비교 대상 TurboGS (arXiv 2606.15924)

---

## 요약

ray 를 sparse 하게 뽑아 학습하면 ray 에 비례하는 비용이 줄어드는 만큼, 남은 고정비의 비중이 커진다. 이번에는 고정비 중 BVH 재구축을 대상으로 삼아, 매 step 전체 재구축을 refit 으로 바꾸고 그 효과를 쟀다.

### 발견 1 — BVH 재구축이 step 시간에서 차지하는 비중이 sparse 에서 dense 의 4 배가 된다

EVER 를 bonsai downsampling 2 에서 재면 step 시간이 `100.1 ns × ray 수 + 41.25 ms` 이고, 이 중 BVH 재구축이 8.4 ms 다. 

dense 는 ray 1,619,801 개로 step 이 203.4 ms 이므로 BVH 가 4.1% 다. 블록 4 로 sparse 하게 뽑으면 ray 가 100,751 개, step 이 51.3 ms 가 되어 같은 8.4 ms 가 16.4% 를 차지한다. **BVH 자체는 느려지지 않았고, 나눌 분모가 작아졌다.**

### 발견 2 — 전체 재구축을 refit 으로 바꾸면 sparse 학습 시간이 14% 줄어든다

bonsai downsampling 2, 블록 4, 30,000 step 기준으로 학습 시간이 23.39 분에서 20.11 분으로 196.4 초 줄었다. step 당 6.55 ms 다. 같은 절감을 dense step 203.4 ms 에 대입하면 3.2% 에 그친다. 절감의 절대량은 같고 체감이 다르다. test PSNR 은 31.849 에서 31.950 으로, 품질 저하는 관측되지 않았다.

### 발견 3 — ray 와 BVH 를 걷어내고 나면 남는 비용은 전부 Gaussian 수에 비례한다

sparse 로 ray 비용을 162.1 ms 에서 10.1 ms 로, refit 으로 BVH 를 8.4 ms 에서 약 1.9 ms 로 줄이면 step 이 약 44.8 ms 가 된다. 그 구성은 optimizer 17.3 ms, backward 고정분 6.1 ms, SH·density·AABB 준비 3.2 ms 로, 모두 ray 가 아니라 primitive 수에 비례하는 항목이다. TurboGS 가 Gaussian 을 2.73M 에서 0.64M 으로 줄인 것도 같은 자리를 겨냥한다.

### 지난 리포트 (2026-08-13) 로부터

- 지난번에 알아낸 것: 잔차 기반 ray 배분이 균등 배분 대비 PSNR 을 0.218 dB 올린다 (t = 7.59).
- 그때 몰랐던 것: 배분 구조로 품질을 올린 뒤에도 남는 학습 시간이 무엇으로 구성되는지, 그리고 그중 코드로 줄일 수 있는 항목이 있는지.
- 이번에 하기로 한 것: 고정비 항목 중 BVH 재구축을 refit 으로 바꾸고 품질과 시간을 잰다.

### 합의 사항 → 상태

- **[완료] BVH refit 경로 구현** — EVER 의 `GAS` 에 `OPTIX_BUILD_FLAG_ALLOW_UPDATE` 와 `refit()` 을 추가했다. 2.2 절.
- **[완료] refit 의 품질 영향 확인** — 네 조건에서 품질 저하가 관측되지 않았다. 2.4 절.
- **[완료] 배분 구조와 함께 적용** — 배분 + refit 이 PSNR 32.092, 20.78 분으로 두 효과가 함께 남는다. 2.3 절.
- **[미착수] dense 에서의 refit 실측** (사유: 발견 2 의 dense 3.2% 는 고정비 모델로 환산한 값이고 실행하지 않았다. dense 1 회가 약 98 분이라 GPU 가 비는 시점이 필요하다) 🔴

### 다음

- 학습시간 절약 측면에서는 optimizer의 비중이 크기 때문에 gaussian 수를 줄이지 않는 선에서 optimizer 시간 줄일 수 있는지 체크
- 근본적인 학습 시간의 원인인 gaussian 수를 품질은 유지하는 선에서 줄일 방법이 있는지 체크
- 교수님 지시 사항(tile샘플링, 이미지 레벨 로스 조사) 수행

## 1. TurboGS 가 학습 시간을 줄인 방법

TurboGS 는 Mip-NeRF 360 에서 3DGS 의 학습시간 891 초를 77 초로 줄이면서 PSNR 은 27.55 에서 27.57 로 유지한다고 보고한다. 우리가 연구하는 방향과 겹치는 부분이 있어 먼저 정리한다. 줄이는 축이 세 개다.

### 1.1 tile 단위 sparse pixel 표집

화면을 16×16 tile 로 나누고, tile 마다 재구성 오차에 따라 표집 비율을 정한다. 오차가 큰 tile 에서는 픽셀을 많이 뽑고, 이미 맞은 tile 은 건너뛴다. 오차는 학습 중에 여러 뷰에 걸쳐 EMA (β = 0.4) 로 유지한다. 한 iteration 에 뷰를 3 장에서 10 장까지 뽑아 함께 쓴다.

우리 배분 구조와 목적이 같다. 다만 단위가 다르다. 우리는 블록 4 또는 5 로 나누는데, TurboGS 는 16×16 을 쓴다. 여기서 쓰는 블록인 tile은 tiling 단계에서 쓰는 tile과 공유하는 것으로 추정된다. turboGS의 코드가 아직 공개되어 있지 않기 때문에 확정을 낼 순 없다. 

### 1.2 iteration 감소

전체 학습을 5,000 iteration 으로 끝낸다 (TurboGS-Big 은 8,000). 3DGS 의 30,000 대비 6 분의 1 이다. densification 은 200 에서 시작해 3,500 에서 끝낸다. 세 축 중 시간에 가장 직접적으로 작용하는 항목이다.

우리는 30,000 step 을 유지하고 있다. step 수를 줄이는 축은 아직 손대지 않았다.

### 1.3 Gaussian 수 감소

오차 기반 density control 로 용량을 배분하고, 학습 끝에 한 번 더 pruning 해서 80~95% 만 남긴다. 결과적으로 Mip-NeRF 360 에서 3DGS 의 2.73M 대비 0.64M 으로 23% 다. rasterization 구조에서도 Gaussian 수가 시간에 직접 작용한다는 뜻이다.

### 1.4 정리

세 축을 함께 적용해 77 초에 도달한다. 장면별로는 82 초에서 104 초 사이에 분포하고, 논문은 "100 초 이내" 로 표현한다. 우리 조건 (bonsai downsampling 2, 30,000 step, 20 분대) 과는 학습 step 수부터 다르므로 시간을 직접 비교할 수는 없다. 다만 어느 축을 남겨두고 있는지는 이 분해로 드러난다. 우리는 1.1 을 하고 있고, 1.2 와 1.3 은 손대지 않았다.

## 2. 남은 시간의 구성과 BVH

### 2.1 왜 BVH 를 먼저 봤는가

배분 구조까지 적용한 뒤에도 학습이 23 분대다. 시간을 더 줄이려면 무엇이 남아 있는지 알아야 한다. EVER 를 bonsai downsampling 2, primitive 1,481,688 개에서 재면 step 시간이 다음과 같다.

```
step(ms) = 100.1 ns/ray × R + 41.25 ms
```

41.25 ms 는 ray 를 0 으로 만들어도 남는다. 그 구성은 아래와 같다.

| 항목 | 시간 | 비례하는 대상 |
|---|---:|---|
| optimizer | 17.3 ms | primitive 수 |
| BVH 재구축 | 8.4 ms | primitive 수 |
| backward 고정분 | 6.1 ms | primitive 수 |
| SH·density·AABB 준비 | 3.2 ms | primitive 수 |
| optix_launch 고정분 | 2.1 ms | — |
| 미분류 | 4.2 ms | — |

이 중 BVH 를 먼저 고른 이유는 코드에 바꿀 여지가 남아 있기 때문이다. optimizer 는 알고리즘을 바꿔야 하지만, BVH 는 OptiX 가 이미 갱신 경로를 제공하는데 EVER 가 쓰지 않고 매 step 전체 재구축을 하고 있었다.

ray 수에 따라 이 8.4 ms 가 차지하는 비중이 달라진다.

| 조건 | ray 수 | ray 비례분 | step 합계 | BVH 비중 |
|---|---:|---:|---:|---:|
| dense | 1,619,801 | 162.1 ms | 203.4 ms | 4.1% |
| sparse 블록 4 | 100,751 | 10.1 ms | 51.3 ms | 16.4% |

dense 에서는 손대도 4% 안에서 움직이지만 sparse 에서는 16% 다. sparse 구조가 BVH 최적화의 값을 올려놓은 셈이다.

### 2.2 refit 이 하는 일

전체 재구축은 primitive 의 경계상자를 다시 읽어 트리 구조를 처음부터 만든다. refit 은 `OPTIX_BUILD_OPERATION_UPDATE` 로 트리의 위상을 그대로 두고 각 노드의 경계상자만 아래에서 위로 다시 계산한다.

위상이 고정되므로 primitive 가 많이 움직이면 트리의 분할이 실제 분포와 어긋나 순회가 느려진다. 다만 경계상자는 항상 자식을 포함하도록 갱신되므로, 순회가 놓치는 primitive 는 생기지 않는다. **품질이 아니라 순회 속도만 나빠지는 구조다.** 그래서 주기적으로 전체 재구축을 섞어 위상을 다시 맞춘다.

EVER 에 다음을 추가했다 (브랜치 `bvh-refit`).

- `GAS` 생성 시 `OPTIX_BUILD_FLAG_ALLOW_UPDATE` 를 붙이는 `allow_update` 인자
- `refit()`, `rebuild()`, `can_refit()` 과 마지막으로 만든 primitive 수 `built_num_prims`
- `EVER_BVH_REFIT=k` 로 k step 마다 전체 재구축하고 나머지는 refit 하는 경로

compaction 은 갱신 가능한 구조에 쓸 수 없으므로 `allow_update` 가 켜지면 건너뛴다. primitive 수가 바뀌면 위상 자체가 달라지므로 `can_refit()` 이 거짓이 되어 전체 재구축으로 넘어간다. densification 이 있는 학습에서는 이 조건이 자주 걸린다.

### 2.3 측정

bonsai downsampling 2, SH 3, 30,000 step, spawn cap 1,500,000, 조건마다 1 회 실행이다. 배분 조건은 블록 5 에 bonus 36,374 를 더해 ray 수를 블록 4 와 같은 100,751 로 맞춘 것이다.

| ray 구조 | refit 주기 | test PSNR | 학습 시간 | 최종 primitive |
|---|---|---:|---:|---:|
| 기준 (블록 4) | 끔 | 31.849 | 23.39 분 | 1,389,762 |
| 기준 (블록 4) | 100 step | 31.960 | 20.29 분 | 1,388,109 |
| 기준 (블록 4) | 200 step | 31.950 | 20.11 분 | 1,388,724 |
| 배분 (블록 5 + bonus) | 끔 | 32.033 | 23.34 분 | 1,420,416 |
| 배분 (블록 5 + bonus) | 200 step | 32.092 | 20.78 분 | 1,420,416 |

기준 조건에서 23.39 분이 20.11 분으로 196.4 초, 14.0% 줄었다. step 당 6.55 ms 이고, 2.1 절의 BVH 8.4 ms 중 78% 에 해당한다. 배분 조건에서는 153.7 초, 11.0% 다.

주기 100 과 200 의 차이는 10.3 초로, 전체의 0.9% 다. 재구축 자체가 전체 시간에서 차지하는 몫이 이미 작아졌으므로 주기를 더 늘려도 얻을 것이 많지 않다.

refit 을 dense 에 적용했을 때의 값은 재지 않았다. step 당 절감 6.55 ms 를 dense step 203.4 ms 에 대입하면 3.2% 다. 절감의 절대량이 같다면 체감은 sparse 쪽이 4 배가 된다.

### 2.4 품질

다섯 조건 모두에서 품질 저하가 나타나지 않았다. 기준 조건은 refit 을 켜서 오히려 0.101~0.111 dB 높고, 배분 조건은 0.059 dB 높다. 이 파이프라인의 실행 간 표준편차가 0.04~0.08 dB 이므로 세 값 모두 실행 간 변동 범위 안이며, refit 이 품질을 올린다고 보기는 어렵다. 확인할 수 있는 것은 떨어뜨리지 않는다는 쪽이다.

별도로 refit 직후의 렌더 결과를 전체 재구축과 비교했을 때 픽셀 차이가 0 이었다. 학습 초반 두 지점에서만 확인한 값이므로 전 구간을 보장하지는 않는다.

## 3. 남은 관문은 Gaussian 수다

sparse 로 ray 비용을, refit 으로 BVH 를 줄이고 나면 step 의 구성이 이렇게 바뀐다.

| 항목 | dense | sparse 블록 4 | sparse + refit |
|---|---:|---:|---:|
| ray 비례분 | 162.1 ms | 10.1 ms | 10.1 ms |
| BVH | 8.4 ms | 8.4 ms | 약 1.9 ms |
| 나머지 고정비 | 32.9 ms | 32.9 ms | 32.9 ms |
| 합계 | 203.4 ms | 51.3 ms | 약 44.8 ms |

44.8 ms 중 ray 에 비례하는 것은 10.1 ms 뿐이다. 나머지 34.7 ms 는 primitive 수를 줄이지 않으면 움직이지 않는다. ray 를 더 줄여서 얻을 수 있는 최대치가 10.1 ms 이므로, 표집 쪽을 더 줄여도 1.29 배가 상한이다.

TurboGS 가 세 축 중 하나로 Gaussian 수를 잡은 것도 같은 이유로 읽힌다. rasterization 구조는 ray tracing 보다 primitive 수의 영향이 작을 텐데도 2.73M 을 0.64M 으로 줄였다. 우리 실행은 1.39M~1.42M 이고 spawn cap 이 1,500,000 이다.

이 자리를 겨냥할 수 있는 항목이 둘 있다.

**optimizer 17.3 ms** — gradient 를 받지 않은 primitive 도 Adam 모멘텀으로 매 step 갱신된다. 3DGRT 에서 `SelectiveAdam` 으로 건너뛰었을 때 bicycle downsampling 4, 1/9 조건에서 PSNR 24.423 에서 24.453 으로 유지하며 31 분 38 초가 21 분 57 초로 1.44 배 빨라졌다. EVER 에는 아직 적용하지 않았다.

**primitive 수 자체** — 어느 primitive 를 줄일 것인지가 남은 질문이다. 8 월 14 일 MCMC 리포트에서 3DGRT 의 미피격 primitive 를 셌을 때 어떤 학습 뷰에서도 gradient 를 받지 못한 것이 MCMC 18.1%, 휴리스틱 10.1% 였다. EVER 에서 같은 값을 재고, 그중 제거해도 품질이 유지되는 범위를 정하는 것이 다음 단계다.

## 4. 한계

- 조건마다 1 회 실행이다. 실행 간 표준편차가 0.04~0.08 dB 이므로 2.4 절의 품질 차이는 단독으로 주장할 수 없다. 시간 차이 196.4 초는 표준편차보다 훨씬 크다.
- 2.1 절의 고정비 분해에서 4.2 ms 가 미분류로 남아 있다.
- 장면이 bonsai 하나다. primitive 수와 분포가 다른 장면에서 BVH 의 비중이 같은지 확인하지 않았다.
- refit 과 전체 재구축의 렌더 일치는 학습 초반 두 지점에서만 확인했다. primitive 가 크게 움직인 뒤의 순회 속도 저하는 재지 않았다.
